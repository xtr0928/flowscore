# migration-guide.md — 文件迁移标准流程与迁移提示词模板

> 本文档定义「旧版/异版数据文件 → 当前版本」的标准迁移流程，并提供可直接复制给 LLM 的迁移提示词模板。
> 面向两类读者：团队成员（手工迁移、审查迁移结果）与参与协作的 LLM（按模板执行迁移）。
> 版本判定、兼容性档位、字段变更语义等契约性内容以 [schema/SCHEMA_RULES.md](../schema/SCHEMA_RULES.md) 为唯一依据；
> 字段表的完整定义以 [docs/file-format.md](file-format.md) 为唯一依据。

## 1. 适用范围与总原则

### 1.1 适用范围

本文档适用于以下情形的数据文件迁移：

- 文件的 `schema_version` 低于当前支持版本（`SUPPORTED.current`），且读取端判定为 `older` 档（详见 SCHEMA_RULES 第 2.2 节）；
- 文件缺失 `schema_version` 字段；
- 文件由异版/分叉工具产出，字段命名或结构与本仓库 schema 不一致；
- 文件中存在当前 schema 未定义的旧字段（需改名或归档）。

**不适用**：`newer` 档（版本高于 `max`）的文件。此类文件按 SCHEMA_RULES 的规定只能 best-effort 加载、原样保留未知字段，**禁止降级迁移**。`legacy` 档（低于 `min`）的文件必须先用旧版工具转换为 `min` 及以上版本，才可套用本文档流程。

### 1.2 总原则

迁移过程必须遵守以下不可协商的原则：

1. **最小改动**：只增改必要字段，禁止顺手「美化」、重排、删除与迁移无关的内容；
2. **保留未知**：无法识别的字段一律放入 `_unknown` 对象原样保留，禁止丢弃；
3. **版本号最后升**：全部字段迁移完成并通过校验后，才将 `schema_version` 升至目标版本；
4. **可回滚**：迁移前必须留存原文件备份，迁移产物写入新文件，禁止原地覆盖；
5. **校验兜底**：迁移产物必须通过目标版本 schema 的完整校验，任何校验错误都视为迁移失败。

## 2. 版本升级标准流程

版本升级遵循固定的五步流程，**顺序不可颠倒**：

```
第一步：读取旧文件     →  第二步：对照新版字段表  →  第三步：增改必要字段
                                                    ↓
第五步：升 schema_version  ←  第四步：Schema 校验
```

### 2.1 第一步：读取旧文件

- 完整读入旧文件，确认其 JSON 语法合法；
- 读取其 `schema_version`（缺失则视为待补，见第 4.1 节）；
- 与 `SUPPORTED` 常量比较，确认落入 `older` 档（逐段数值比较，禁止字符串比较，规则见 SCHEMA_RULES 第 2.2 节）；
- 备份原文件（如 `data.old.json`），迁移产物另存为新文件（如 `data.json`）。

### 2.2 第二步：对照新版字段表

- 打开 [docs/file-format.md](file-format.md) 中目标版本的字段表；
- 逐字段比对，将旧文件字段分为三类：
  - **一致**：名称、类型、语义均与新版一致 → 原样保留；
  - **需增改**：新版要求而旧文件缺失，或名称/结构有变 → 记录到迁移清单；
  - **未知**：旧文件中存在但新版字段表没有的字段 → 待放入 `_unknown`。
- 产出一份明确的「字段级迁移清单」，作为第三步与第 3 节提示词模板中「字段清单」的输入。

### 2.3 第三步：只增改必要字段

- 严格按迁移清单操作，逐条完成：
  - 缺失且 schema 声明了 `default` 的字段，填入默认值；
  - 缺失且无默认值的可选字段，**不强行捏造**，保持缺失即可（可选字段缺失必须合法，见 SCHEMA_RULES 第 3.1 节）；
  - 需改名的字段，执行「新增新名 + 旧值搬移 + 旧名移入 `_unknown`（保留原始痕迹）」；
  - 未知字段整体搬入顶层 `_unknown` 对象，键名与原值原样保留。
- 此阶段**不修改** `schema_version`。

### 2.4 第四步：用 Schema 校验

- 用目标版本的 `schema/*.json` 对迁移产物做完整校验；
- 校验器仅支持 SCHEMA_RULES 第 4 节白名单内的关键字，白名单外关键字会被「忽略并告警」，**告警本身不代表迁移失败，但必须人工确认告警字段不影响语义**；
- 任何 `required` 缺失、类型不符、枚举越界等硬错误，都必须回到第三步修正后重新校验；
- 校验失败时禁止通过放宽 schema 来「让数据通过」。

### 2.5 第五步：升 `schema_version`

- 确认第四步校验全绿后，将顶层 `schema_version` 写为目标版本号（与 `SUPPORTED.current` 一致）；
- 再次运行一次校验（确认版本字段本身的格式约束 `^\d+\.\d+\.\d+$` 通过）；
- 记录迁移日志：源版本 → 目标版本、迁移日期、字段清单摘要、`_unknown` 中保留了哪些键。

## 3. 迁移提示词模板（可整段复制）

本节模板用于将迁移任务交给 LLM 执行。**以下代码块内的全部内容必须与界面「复制迁移提示词」按钮产出的文本逐字一致**；按钮的功能即把模板中的占位符替换为当前上下文实参后整段复制。若本模板与按钮产出文本发生分歧，以修复两者一致性为最高优先级，任何一方不得单独修改。

使用方法：复制下方模板，将 `{{...}}` 占位符替换为实际内容（界面按钮会自动完成替换），连同待迁移 JSON 一起发送给 LLM。

```text
你是数据文件迁移助手。请将下面提供的 JSON 数据文件迁移到 schema_version {{TARGET_VERSION}}。

【当前状态】
- 数据文件当前 schema_version：{{CURRENT_VERSION}}（若为「缺失」则需按规则补齐）
- 目标 schema_version：{{TARGET_VERSION}}

【字段清单】
{{FIELD_LIST}}

【当前版本 Schema 摘要】
{{SCHEMA_SUMMARY_OLD}}

【目标版本 Schema 摘要】
{{SCHEMA_SUMMARY_NEW}}

【迁移规则（必须全部遵守）】
1. 只增改必要字段：仅完成字段清单中列出的增、改操作，禁止重排键顺序，禁止改动任何与迁移无关的内容。
2. 缺失且 Schema 声明了 default 的字段，填入该默认值；缺失且无默认值的可选字段，保持缺失，不捏造值。
3. 需要改名的字段：新增新名字段并搬移旧值，同时把旧字段名与旧值原样记录到顶层 _unknown 对象中。
4. 当前 Schema 无法识别的字段，一律原样放入顶层 _unknown 对象，禁止丢弃、禁止改写其值。
5. _unknown 对象中已有的条目原样保留，不做合并、不去重、不排序。
6. 全部字段迁移完成后，将顶层 schema_version 改为 {{TARGET_VERSION}}。
7. 迁移结果必须能通过目标版本 Schema 的校验；若你判断某字段无法满足目标 Schema 约束，不要静默篡改，在 _unknown 中保留原始值并在 _migration_notes 数组中追加一条说明。

【输出要求（硬性约束）】
- 只输出迁移后的完整 JSON，不要输出任何解释、注释、Markdown 代码围栏或多余文字。
- 输出必须是单个合法 JSON 对象，UTF-8 编码，键名与值不加任何前后缀修饰。
- 未知字段必须放入 _unknown，禁止省略。

【待迁移的 JSON 数据】
{{JSON_CONTENT}}
```

### 3.1 占位符说明

| 占位符 | 含义 | 填写要求 |
|---|---|---|
| `{{TARGET_VERSION}}` | 目标 `schema_version` | 通常等于 `SUPPORTED.current` |
| `{{CURRENT_VERSION}}` | 旧文件当前的 `schema_version` | 缺失时填字面量「缺失」 |
| `{{FIELD_LIST}}` | 字段级迁移清单 | 按第 2.2 节方法产出，逐条写明「字段名 → 操作（新增默认值/改名/移入 _unknown）」 |
| `{{SCHEMA_SUMMARY_OLD}}` | 旧版本 Schema 摘要 | 含顶层字段名、类型、required 列表、枚举值 |
| `{{SCHEMA_SUMMARY_NEW}}` | 目标版本 Schema 摘要 | 同上，两份摘要的差异处即迁移要点 |
| `{{JSON_CONTENT}}` | 待迁移的完整 JSON | 原样粘贴，不做任何预处理 |

### 3.2 收到 LLM 输出后的处理

1. 解析输出，确认是单个合法 JSON（若包含围栏或解释文字，视为任务失败，要求重出）；
2. 按第 5 节自检清单逐项核对；
3. 用目标版本 schema 跑一次完整校验；
4. 校验通过后，将结果与原文件一并归档，并记录迁移日志。

## 4. 手工迁移：三种常见场景

以下场景可不经 LLM 直接手工完成。每个场景均须遵守第 2 节的步骤框架（备份 → 修改 → 校验 → 升版本），此处只列出各场景的字段级操作要点。

### 4.1 场景一：补 `schema_version`

**典型症状**：加载时提示「数据缺少版本信息」，读取端按 `legacy` 预处理（见 SCHEMA_RULES 第 2.2 节判定实现要求）。

**操作步骤**：

1. 打开 JSON 文件，在顶层对象中新增键 `schema_version`；
2. 值填目标版本号字符串，格式必须匹配 `^\d+\.\d+\.\d+$`（如 `"1.0.0"`，禁止 `"1.0"` 或 `"01.0.0"`）；
3. 逐一核对文件其余字段与目标版本字段表（[docs/file-format.md](file-format.md)）的一致性——补版本号**不等于**迁移完成，若文件本身是异版结构，还需继续执行场景二或场景三；
4. 用目标版本 schema 校验通过后保存。

```json
{
  "schema_version": "1.0.0",
  "其余字段": "保持原样"
}
```

### 4.2 场景二：补 `runtime` 段

**典型症状**：旧版文件没有 `runtime` 段，新版字段表中该段为可选但含默认值语义，读取端虽能容忍缺失，但为获得完整功能需补齐。

**操作步骤**：

1. 查阅目标版本 schema 中 `runtime` 段的字段定义与 `default` 声明；
2. 在顶层新增 `runtime` 对象，逐个内部字段填入 schema 声明的默认值：

```json
{
  "schema_version": "1.0.0",
  "runtime": {
    "此处各键": "按 schema 中 default 逐项填写"
  }
}
```

3. 若旧文件中以**平铺**形式存在本应属于 `runtime` 的键（如顶层的 `engine`、`mode` 等），将这些键的值搬入 `runtime` 对应位置，原平铺键移入 `_unknown` 保留痕迹；
4. 注意：`runtime` 若在目标 schema 中为**可选**（不在 `required` 中），保持缺失也是合法的——是否补齐取决于是否需要新功能，而非校验压力；
5. 校验通过后保存。

### 4.3 场景三：旧字段改名

**典型症状**：异版工具产出的文件使用了旧字段名（如 `create_time` → 新版 `created_at`）。按 SCHEMA_RULES 第 1.2 节，改名属于破坏性变更（MAJOR 级），迁移时必须保留旧名痕迹。

**操作步骤**：

1. 在字段表中确认新旧字段名、类型与语义的对应关系，确认仅是改名而非语义变化（若语义也变了，须额外做值的转换，转换规则写入迁移清单）；
2. 新增新字段名，值原样搬移（类型不变时禁止任何值改写）；
3. 在顶层 `_unknown` 对象中记录旧字段名与旧值：

```json
{
  "schema_version": "1.0.0",
  "created_at": "2024-01-01T00:00:00Z",
  "_unknown": {
    "create_time": "2024-01-01T00:00:00Z"
  }
}
```

4. 若同一旧字段在数组元素等嵌套位置出现，逐位置执行相同的「新增 + 搬移 + 归档」操作；
5. 校验通过后保存。

## 5. 迁移后自检清单

迁移产物交付或合入前，逐项打勾确认。**任何一项未通过，均视为迁移失败，须回退修正。**

### 5.1 结构与版本

- [ ] 顶层 `schema_version` 等于目标版本，且匹配 `^\d+\.\d+\.\d+$`；
- [ ] 产物通过目标版本 `schema/*.json` 的完整校验，无 `required` 缺失、类型不符、枚举越界等硬错误；
- [ ] 校验器对白名单外关键字的告警已逐条人工确认（见 SCHEMA_RULES 第 4 节），不影响语义；
- [ ] 原文件备份完好，迁移产物写入的是新文件，未原地覆盖。

### 5.2 字段完整性

- [ ] 迁移清单中列出的每一项操作都已执行，无遗漏、无多余；
- [ ] 所有 schema 声明了 `default` 的缺失字段已填入默认值；
- [ ] 无默认值的可选字段未被捏造值（缺失保持缺失）；
- [ ] 改名字段：新名已就位、旧值未改写、旧名已归档至 `_unknown`；
- [ ] 与迁移无关的字段、键顺序、值内容零改动。

### 5.3 未知字段与痕迹

- [ ] 所有无法识别的字段均已放入 `_unknown`，键名与值原样保留；
- [ ] `_unknown` 中既有的条目未被合并、去重或排序；
- [ ] 无法满足目标 schema 约束的字段已在 `_migration_notes` 中留有说明（如适用）。

### 5.4 流程与记录

- [ ] 若迁移由 LLM 完成，其输出为纯 JSON，无解释文字与代码围栏（见第 3.2 节）；
- [ ] 迁移日志已记录：源版本 → 目标版本、日期、字段清单摘要、`_unknown` 保留键列表；
- [ ] 若本次迁移暴露出 schema 本身需要变更的需求，已按 SCHEMA_RULES 第 3 节「先改 schema → 再改代码 → 最后升版本号」的流程另行立项，**未在迁移产物中顺手夹带 schema 变更**。
