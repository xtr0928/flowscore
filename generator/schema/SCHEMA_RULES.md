## 1. 版本号规则

### 1.1 版本格式

所有 `schema/*.json` 的顶层 `$version` 字段（本项目自定义字段，非 JSON Schema 标准字段）必须遵循语义化版本格式：

```
MAJOR.MINOR.PATCH
```

- `MAJOR`：主版本号，不兼容变更时递增；
- `MINOR`：次版本号，向后兼容的功能新增时递增；
- `PATCH`：修订号，不改变 schema 结构语义的修正时递增。

三段均为非负整数，不允许前导零（`01` 非法），不允许省略段（`1.0` 非法）。
正则校验：`^\d+\.\d+\.\d+$`

### 1.2 三类变更语义

判定一次变更属于哪一档，唯一依据是「旧数据在新 schema 下的命运」：

| 变更类型 | 典型操作 | 版本影响 | 判定理由 |
|---|---|---|---|
| **破坏性变更** | ① 删除已有字段；② 改变字段语义（含更名、含义收窄/放宽、单位变化）；③ 改变 `kind` 取值或结构 | `MAJOR` 递增，`MINOR`/`PATCH` 归零 | 旧数据或旧代码在新 schema 下会出错或静默产生错误结果 |
| **兼容性新增** | ① 新增**可选**字段（不得同时设为 required）；② 向已有枚举中追加新值 | `MINOR` 递增，`PATCH` 归零 | 旧数据仍完全合法，旧代码可忽略新字段 |
| **非结构修正** | ① 文档描述、注释、title 修正；② 不破坏旧数据的收紧校验（如原来无上限的字符串加 `maxLength`，且确认存量数据全部通过） | `PATCH` 递增 | 不改变任何合法数据集的判定结果 |

**特别提醒（面向 LLM）：**

- 「加枚举值」在**读取端**是 MINOR，但若该枚举值会被写回/序列化，且旧版本读取端遇到未知枚举会报错，则必须评估是否应为 MAJOR；本项目默认按 MINOR 处理，读取端遇到未知枚举必须容忍（见第 4 节）。
- 「把可选字段改为必填」属于删语义级别的破坏性变更，按 MAJOR 处理，禁止以 MINOR 蒙混。
- 一次提交若同时包含 MINOR 与 MAJOR 性质的变更，整体按 MAJOR 计。

## 2. 版本支持矩阵与兼容判定表

### 2.1 支持版本常量

当前代码库唯一认定的支持矩阵（读取端能力声明）：

```json
{
  "SUPPORTED": {
    "current": "1.0.0",
    "min": "1.0.0",
    "max": "1.0.0"
  }
}
```

- `current`：随代码发布进度同步维护的当前版本；
- `min`：读取端能容忍的最低版本，低于此版本判为 `legacy`；
- `max`：读取端能识别的最高版本，高于此版本判为 `newer`。

**修改规则**：发布 MINOR/MAJOR 变更时，`current` 与 `max` 同步递增；`min` 仅在主动放弃旧格式支持时递增。该常量在代码与 `index.html` 中各有一份内联拷贝，必须等价（见第 5 节）。

### 2.2 四档兼容判定表

读取端在加载数据文件时，取数据文件的 `$version` 与 `SUPPORTED` 比较，落入以下四档之一：

| 档位 | 判定条件 | 含义 | UI 行为 |
|---|---|---|---|
| `legacy` | `version < min` | 数据格式过于古老，读取端无法可靠解析 | 阻断加载。弹出模态错误对话框：「数据版本过旧（vx.y.z），请使用旧版工具转换后再导入」，并提供版本号展示；不渲染任何主界面内容 |
| `older` | `min ≤ version < current` | 数据可解析，但缺少新版本功能 | 正常加载并渲染。在页面顶部显示**可关闭**的提示条：「数据为旧版本 vx.y.z，部分新功能不可用」。数据可编辑，保存时**保持原版本号**，不擅自升级 |
| `ok` | `version == current` | 版本完全匹配 | 正常加载、正常渲染，无任何版本提示。保存时版本号不变 |
| `newer` | `version > max` | 数据由更新版本的工具产出，可能含有本端无法理解的结构 | 尽力加载（best-effort），未知字段原样保留。页面顶部显示**常驻且不可关闭**的警告条：「数据版本较新（vx.y.z），可能存在本版本无法展示的内容，编辑保存可能丢失新增信息」。保存时**保持原版本号**，禁止降级 |

**判定实现要求**：

- 版本比较必须按 `MAJOR`、`MINOR`、`PATCH` 三段数值逐段比较，禁止字符串直接比较（`"0.9.0" < "1.0.0"` 字符串比较结果错误）。
- 数据文件缺失 `$version` 字段时，按 `legacy` 处理，提示「数据缺少版本信息」。
- `older`/`newer` 两档保存数据时**一律原样保留未知字段**，禁止读取端删除或改写其不理解的内容。

## 3. 新增字段流程

新增字段（或其他任何 schema 变更）必须严格遵循以下三步顺序，**不可颠倒、不可跳步、不可合并为一次提交**：

```
第一步：改 schema          第二步：改代码            第三步：升版本号
schema/*.json 新增字段  →  读写逻辑适配新字段     →  更新 $version 与
（保持 optional）          （读取端容忍缺省）        SUPPORTED 常量
```

### 3.1 第一步：先改 schema

- 在 `schema/*.json` 中新增字段定义，必须标记为可选（不出现在 `required` 数组中）；
- 若字段有默认值语义，在 schema 中通过 `default` 关键字声明；
- 此步合入后，CI 中「旧数据对新 schema」的校验必须仍然全绿（旧数据不含新字段也合法）。

### 3.2 第二步：再改代码

- 读取端：字段缺失时使用 schema 中声明的 `default`（或代码内兜底值），不得抛错；
- 写入端：按新逻辑产出该字段；
- `index.html` 中与该字段相关的内联常量、UI 逻辑同步更新；
- 此步合入后，新旧代码产出的数据在双方读取端均应正常工作。

### 3.3 第三步：最后升版本号

- 按第 1.2 节判定本次变更档位，更新 `schema/*.json` 的 `$version`；
- 同步更新代码与 `index.html` 中的 `SUPPORTED` 常量；
- 触发第 5 节的对账校验，确认三处版本号一致。

### 3.4 为什么顺序不可颠倒

| 错误顺序 | 后果 |
|---|---|
| 先改代码后改 schema | 代码产出的数据在过渡期无法通过 schema 校验，CI 与外部校验工具报错 |
| 先升版本号后改代码 | 读取端声明支持一个自己尚不理解的版本，`newer` 档判定失真 |
| 三步合并一次提交 | 出错时无法回滚定位，且违反「每步独立可验证」原则 |

## 4. 校验器关键字白名单与排除清单

项目内置的轻量 JSON Schema 校验器**只支持以下关键字子集**。schema 文件中出现白名单之外的关键字时，校验器行为是「忽略并告警」，而非报错。

### 4.1 支持关键字白名单

| 类别 | 关键字 |
|---|---|
| 根/组合 | `$schema`、`$version`（自定义）、`type`、`title`、`description` |
| 对象 | `properties`、`required`、`additionalProperties`、`minProperties`、`maxProperties` |
| 字符串 | `minLength`、`maxLength`、`pattern`、`format`（仅支持 `date`、`date-time`、`email`、`uri`） |
| 数值 | `minimum`、`maximum`、`exclusiveMinimum`、`exclusiveMaximum`、`multipleOf` |
| 数组 | `items`、`minItems`、`maxItems`、`uniqueItems` |
| 枚举/常量 | `enum`、`const` |
| 组合逻辑 | `oneOf`、`anyOf`（`allOf` 见排除清单） |
| 元信息 | `default`、`deprecated`、`examples` |

### 4.2 有意排除清单（排除理由必须保留，禁止 silently 删除条目）

| 排除关键字 | 排除理由 |
|---|---|
| `allOf` | 组合展开逻辑复杂，且本项目所有 schema 均可用扁平结构表达；引入会显著增加校验器体积与出错面 |
| `not` | 否定逻辑在错误信息中难以给出可读提示，违背「错误信息可指导修复」目标 |
| `$ref` / `$defs` / `$anchor` | 项目 schema 规模小，无需引用机制；且跨文件引用会破坏「单文件自包含」分发约束 |
| `if` / `then` / `else` | 条件校验引入状态耦合，维护成本高于收益；如需条件逻辑应由代码层承担 |
| `dependentRequired` / `dependentSchemas` | 同上，条件依赖逻辑下沉到代码层 |
| `patternProperties` / `propertyNames` | 动态键名校验场景本项目不存在 |
| `contains` / `minContains` / `maxContains` | 数组元素存在性校验场景本项目不存在 |
| `contentEncoding` / `contentMediaType` | 二进制内容不属于本项目数据模型 |
| `format`（除白名单四种外的值） | 如 `uuid`、`ipv4` 等格式校验依赖正则实现差异，跨端一致性无法保证 |

**规则**：

- 若未来需要引入白名单之外的关键字，必须先更新本节（白名单或排除清单二选一），并说明理由，评审通过后方可使用——**schema 文件永远不得先于本契约使用未收录关键字**。
- 校验器遇到排除清单中的关键字时，输出告警日志：`[schema-warn] 忽略不支持的关键字: <keyword>`，随后忽略该关键字继续校验，不中断。

## 5. schema 与 index.html 内联常量对账

### 5.1 对账范围

以下三处必须保持**语义等价**，任何一处单独变更即构成缺陷：

1. `schema/*.json` 中的 `$version` 字段；
2. `index.html` 中内联的 `SUPPORTED` 常量（含 `current` / `min` / `max`）；
3. 校验器/业务代码中引用的 `SUPPORTED` 常量。

「等价」定义：三处出现的版本号字符串逐字符相同，且 `current` 与 schema 的 `$version` 相等。

### 5.2 对账方法

**方法一：读取比对**

1. 解析 `schema/*.json`，提取顶层 `$version`；
2. 从 `index.html` 源码中定位 `SUPPORTED` 常量定义（约定以 `const SUPPORTED` 或等价形式内联于 `<script>` 块中），提取三个版本号；
3. 断言：
   - `schema.$version === SUPPORTED.current`；
   - `index.html` 中的 `SUPPORTED` 与代码中的 `SUPPORTED` 逐字段相等；
   - `min ≤ current ≤ max`（按三段数值比较）。

**方法二：运行时自检（可选，浏览器端）**

页面加载时，校验器读取内嵌或 fetch 的 schema，比较 `$version` 与 `SUPPORTED.current`，不一致时在控制台输出 `console.error` 并在页面顶部渲染红色告警条。

### 5.3 测试入口

对账校验以自动化测试形式固化，测试入口约定如下：

| 入口 | 位置 | 说明 |
|---|---|---|
| CI 对账测试 | `tests/schema-consistency.test.js`（或等价测试文件）中的 `describe("schema/index.html 版本对账")` 用例 | 执行 5.2 方法一的三个断言；任何 schema 或 `index.html` 变更的 MR 必须使该用例通过 |
| 本地手动入口 | 仓库根目录执行 `npm test -- --filter schema-consistency`（或项目 README 中声明的等价命令） | 开发者改完版本号后本地自检 |
| 浏览器端自检 | `index.html` 打开时自动执行的方法二 | 兜底防线，捕获「CI 通过后文件被单独改动」的场景 |

**失败处理**：对账测试失败的 MR 不允许合入。修复方式永远是回到第 3 节的三步流程补齐遗漏步骤，而不是手改某一份常量「让测试变绿」。
