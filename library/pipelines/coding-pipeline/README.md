# 协同编码管线（执行段）

> 四模型分工：DS 编排 → GLM 设计 ∥ Qwen 视觉 → Kimi 编码 → 审查 → DS 集成

## 这份管线解决什么

把一段自然语言需求，变成**一套可交付的代码**。

它不靠单个模型硬扛，而是**让四个模型各自做最擅长的事**，并且**把审查做成两个互相独立的关卡**：

```
① 需求理解（DS）      把口语需求拆成结构化规格
② 整体设计（GLM）      文件清单 + 接口约定
③ 视觉规格（Qwen）     界面结构与视觉要求（独立于②，只忠于需求）
④ 逐文件编码（Kimi）   按设计逐个产出代码文件
⑤ 代码审查（GLM）  ┐
⑥ 安全审查（DS）   ┴→ 两份都到齐才进汇合（mode: all）
⑦ 汇总修复（DS）      合并两份审查 + 可选的视觉审查，产出最终代码
```

**两个设计要点**：

- **③ 视觉规格从 ① 取输入，而不是从 ②** —— 让视觉判断忠于用户原始需求，不被设计者的组织方式带偏。
- **⑦ 的视觉审查是可选端口（`required: false`）** —— 代码质量与安全审查是阻断项（缺了不该发），视觉审查是增强项（缺了照跑）。这个区别在旧格式里**无处可写**，是本格式新增 `required` 的原因。

## 怎么跑

```bash
# 用流谱生成器打开（可视化查看 / 二次编辑）
#   管线库 → 这条管线 → 「用生成器打开」
# 或直接生成器里拖入 pipeline.flow.json

# 命令行直接跑本体实现
cd src
export DEEPSEEK_API_KEY=***  GLM_API_KEY=***  KIMI_API_KEY=***  QWEN_API_KEY=***
python3 planning.py            # 规划段（① 需求澄清，需人工拍板）
python3 coding_pipeline.py     # 执行段（②-⑦ 全自动）
```

## 前置条件

- **四个模型端点同时在位**（DeepSeek / GLM / Kimi / Qwen）。缺一条会在对应节点报错停下。
- 一个可写的工作目录（默认 `deliverables/`）。
- 规划段需要**人工拍板**：选题、需求澄清、选型都不能自动跳过。

## 注意事项

- **整条管线约 20 分钟，消耗约 8 万 token**。首次运行建议先用 sample 试跑验证环境。
- **`planning.py` 不是全自动的** —— 它的第 ①②③ 步会停下来等人确认。这是刻意的：需求没聊清就开写，返工成本远高于省下的时间。
- **四个模型的上下文窗口不一样**。④ 逐文件编码设了 32K `max_tokens`，喂进去的设计文本不能超过对应模型窗口。
- **本格式的 `note` 节点在这里有两处用法**：`编码约定` 是**接线型**（注入到 ④ 的 system 提示词，改它等于改行为）；`关于汇总修复的提醒` 是**挂靠型**（只贴在人看的画布上，不注入）。
