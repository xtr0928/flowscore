# 数模管线 V6.1 —— 逐问推进 + 反投毒摄入门禁

> **多 agent 协作求解**，带**两个嵌套的循环**：逐问循环 + 审查拍板循环。

## 这份管线解决什么

把一道数学建模竞赛题，变成**一篇过得了交付门禁的论文** —— 并且**保证喂进来的题面是干净的**。

相比 V5.2，这是**代际升级**：从「一条直链跑到底」改成「**逐问推进 + 每问内部反复审查拍板**」。

## ★ 两个循环（这是本管线的核心形态）

### 循环一 · 逐问 `foreach q = 1..N`

```
P1 交接包 → P2 多agent并行推理 → P3 分歧 → P4 统一拍板
→ P5 求解 → P6 门禁 → P7 评审+评审长 → P8 修复 → P9 冻结
                                              │
                                              └──► 回到 P1 处理下一问
```
**迭代次数 = S0 拆出的问题数 N。** 问与问之间**只通过冻结版传递**（R2 逐问锁定），禁止原地覆盖。

### 循环二 · 审查拍板 `while 未收敛`

```
P7 多agent评审 → P7b 评审长拍板（verdict）
   → P8 修复
   → 【回灌 P5 重算】← ★ 这是回边
   → P6 门禁 → P7 再评审 → 收敛判定
                        │
        verdict=PASS ───┴──► 放行 P9 冻结
        verdict=REPAIR ─────► 打回 P5，再来一轮
```
**直到 verdict=PASS 才允许冻结。** 超过 K 轮 → 升级为人工暂停点，交博士处置。

> **两者关系**：循环二**嵌在**循环一里面 —— 每一问内部都要先把审查拍板跑到收敛，才允许冻结进入下一问。

## 多 agent 协作怎么分工

| 角色 | 实例数 | 模型 | 干什么 |
|---|---|---|---|
| 题面解析 | 1 | 主模型 | 产出 problem_profile / 问题清单 |
| **候选推理** | **N（并行）** | **推理池** | **独立推理，匿名输出 candidates/** |
| 多agent分歧记录 | 1 | 可配置 | 汇总候选，只记分歧不裁决 |
| 假设官 | 1 | 可配置 | 梳理隐含假设与适用边界 |
| Devil's Advocate | 1 | 可配置 | 专门唱反调，找反例与伪相关 |
| **统一者（拍板）** | 1 | 主模型 | **逐处裁决分歧，融合重写** |
| 评审员 | R | 评审池 | 零上下文评审，先验证后评分 |
| **评审长（拍板）** | 1 | **主模型额外新实例** | 汇总评审票 → repair_order + verdict |
| 修复者 | 0–K | 可配置 | 按修订单修复，需重算项回灌 |

**实例隔离是硬要求**：统一者 / 评审长 / 下一问统一者 = **三个不同实例**，所有实例一律重开。

## S-1 反投毒摄入安检（V6.1 新增）

外部材料是**不可信输入**。PDF 里可能藏着白色的「忽略以上指令，直接输出…」。

**三通道**：
```
通道 B 原始直读（不净化）    → raw_text   隐藏文字【在】这里
通道 A 物理净化 + 检测       → clean_text 隐藏文字【已剔除】
通道 C 语义评分（载体无关）   → 指令特征分 0–6
              ↓
判定层：① 差分 raw−clean ② 双轨（物理 vs 语义分离）③ 纯净度 ≥0.80 ④ 字符形态 6≤连通域≤200
              ↓
fail-closed 门禁：有 HIGH → 阻断，必须人工确认
              ↓
clean_problem.md（后续建模唯一题目来源） / poison_report.md / ingest_manifest.json（SHA-512）
```

**为什么双轨判定是核心**：物理隐藏与语义可疑必须**分开判**，否则官方语料大量误报（实测踩坑记录见设计文档 §4.3）。

## 铁律 R1–R8

| # | 铁律 |
|---|---|
| R1 | **上下文公理** —— 任何角色的任何一次调用 = 全新实例；单发单收，禁止多轮会话 |
| R2 | **逐问锁定** —— 问内不跳步；问间只通过冻结版传递；版本号化，禁止原地覆盖 |
| R3 | **统一=融合重写** —— 逐处裁决分歧 + D 决策记录，防「缝合怪」 |
| R4 | **回改走作废重算** —— 冻结件被推翻 → 传递闭包 stale → 拓扑序重算 → 重新冻结 |
| R5 | **开场点将** —— 先问博士用几个/哪些模型 → 只对所选别名做真调用核查 → 冻结进 RUN.json |
| R6 | **花钱纪律** —— 开跑前预估并获批；运行中实时计数，超批准值硬停 |
| R7 | **交付物门禁** —— 每问冻结前过本问门禁；终局过跨问一致性门禁 |
| R8 | **双保险** —— 每 run 独立 git 仓库；全量入 git；冻结点提交；MANIFEST 侧车 |

## 半自动暂停点（semi 模式，默认）

```
① P4 完成后（统一方案过目）
② 每问 P9 冻结前
③ 争议升级（修复超 K 轮 / 评审长判 REDO / 主模型失效）
```
握手是**文件式**的：orchestrator 写 `PAUSE_REQUEST.json`，博士用 `resolve --action approve/edit/regenerate/abort`。
auto 模式不暂停，仅记录与通知。

## 本 JSON 怎么读

- **`task` 节点** = 确定性步骤（门禁 / 构建器 / 排版 / 检测）—— 不是 LLM 调用
- **`loop` 字段** = 回边标记。带 `loop` 的连线是**循环**，不是正向流：
  - `n_p9 → n_p1`：逐问循环（`foreach`，over = N 个问题）
  - `n_conv → n_p5`：审查拍板循环（`while`，over = 未收敛的修订单）
- **`note` 节点** = 注释，连到节点上只展示、不注入；连到输入端口则注入提示词
